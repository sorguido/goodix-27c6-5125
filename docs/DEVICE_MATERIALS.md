# Preparing the device-specific material set

The Goodix `27c6:5125` runtime needs five files before it can open a secure
session with the fingerprint reader.

This page is written for a first-time user. You do not need to know the
project history, the internal test names, or the Goodix protocol before
following it.

> **Important:** the material belongs to one physical fingerprint reader.
> Never copy a secret, cache, or material bundle from another reader. Never
> generate a replacement PSK, flash firmware, run IAP/ClearApp, or write OTP.

The final directory must contain exactly these files:

```text
goodix-material/
├── target-material-manifest.json
├── transport-material.bin
├── target-config-90.bin
├── gfusb.dll
└── fdt-cache.bin
```

If you already have a validated five-file bundle for your reader, skip to
[Part 6 — Verify the five-file bundle](#part-6--verify-the-five-file-bundle).

If you do **not** already have the bundle, start with Part 1.

---

## Part 1 — Understand what comes from Windows and what is generated

The five files do not all come directly from Windows.

| Final file | Where it comes from |
| --- | --- |
| `gfusb.dll` | copied unchanged from the exact OEM Goodix driver package used for the reader |
| `fdt-cache.bin` | Windows OEM file `C:\ProgramData\Goodix\goodix.dat`, copied unchanged and renamed |
| `target-config-90.bin` | extracted from a USB capture made while the OEM Windows stack initializes the same reader |
| `transport-material.bin` | generated from the reader secret recovered from `Goodix_Cache.bin` by Windows DPAPI, then finalized on Linux into the runtime `G5125POC` format |
| `target-material-manifest.json` | generated by project tooling from the qualified device material and validated reader responses |

The OEM Windows environment is therefore used to obtain the raw inputs. Some
of the final Linux files are project-generated outputs.

### Public helper tools

The public source tree contains the helper path for both
`transport-material.bin` and `target-config-90.bin` under:

```text
tools/device-materials/
```

For transport material, use:

```text
Export-Goodix5125TransportMaterial.ps1
Finalize-Goodix5125TransportMaterial.py
```

For CONFIG90 extraction from a Windows USBPcap capture, use:

```text
Extract-Goodix5125Config90.py
```

The CONFIG90 extractor is offline-only and has a synthetic self-test. It does
not open or write the fingerprint reader. A newly extracted file is
reader-specific. The runtime accepts it when its protocol finalizer is valid
and its digest matches the manifest generated for the same user bundle.

Do not try to recreate CONFIG90 by cutting arbitrary bytes out of Wireshark and
do not invent or provision a replacement PSK.

## Part 2 — Prepare the OEM Windows environment

You can use either:

- an existing Windows installation on the computer that contains the Goodix
  reader; or
- a Windows virtual machine running on the Linux computer, with the **same
  physical Goodix `27c6:5125` reader** attached to the VM by USB passthrough.

The project validated the second path on a Linux-only machine: a fresh Windows
VM, the OEM Goodix driver, and the same physical fingerprint reader were enough
for the OEM stack to create fresh cache material again.

### 2.1 If Windows is already installed

1. Boot Windows normally.
2. Confirm that the Goodix fingerprint reader is present in Device Manager.
3. Confirm that the OEM Goodix driver is installed.
4. For the qualified release, the OEM driver version is `1.1.125.14`.
5. Do not replace firmware, clear the application, provision a new key, or run
   any Goodix maintenance utility that changes persistent device state.
6. Continue with [Part 3](#part-3--collect-the-oem-files).

### 2.2 If the computer is Linux-only

Use a Windows VM.

Before attaching the reader to Windows, verify on Linux that the device exists:

```bash
lsusb -d 27c6:5125
```

Expected result: one line describing a USB device with VID:PID `27c6:5125`.

Start the Windows VM **without** attaching the fingerprint reader yet.

Inside Windows, open PowerShell and check that the reader is absent:

```powershell
Get-PnpDevice -PresentOnly | Select-String 'VID_27C6&PID_5125'
```

Expected result before passthrough: no matching output.

Install the OEM Goodix driver package in Windows. For the qualified release,
use version `1.1.125.14`.

Now attach the **same physical** Goodix reader to the VM using your VM
manager's USB-passthrough control. Do this once; do not detach/re-attach the
reader repeatedly.

Run the check again:

```powershell
Get-PnpDevice -PresentOnly | Select-String 'VID_27C6&PID_5125'
```

Expected result: Windows now reports the Goodix device.

Allow the OEM stack to initialize the reader. You do not need to flash the
reader or create a replacement key. The objective is only to let the normal
OEM driver create its local cache files for this physical device.

## Part 3 — Collect the OEM files

Create a private working directory outside Git and outside cloud-synchronized
folders. For example, in PowerShell:

```powershell
New-Item -ItemType Directory -Force C:\GoodixMaterialWork
```

Do not use OneDrive, Dropbox, Google Drive, a public share, or a repository
folder for generated secret material.

### 3.1 Check for the Goodix cache directory

In PowerShell:

```powershell
Get-ChildItem 'C:\ProgramData\Goodix' -Force
```

The two important OEM cache files are:

```text
C:\ProgramData\Goodix\Goodix_Cache.bin
C:\ProgramData\Goodix\goodix.dat
```

If the directory or files do not exist, stop. The OEM stack has not created
all required local material yet. Do not manufacture empty placeholder files.

### 3.2 Copy `goodix.dat`

Copy it into the private working directory:

```powershell
Copy-Item 'C:\ProgramData\Goodix\goodix.dat' 'C:\GoodixMaterialWork\fdt-cache.bin'
```

Expected result:

```text
C:\GoodixMaterialWork\fdt-cache.bin
```

For the qualified material set its exact size is:

```text
13,520 bytes
```

The file is copied byte-for-byte. Only the filename changes.

### 3.3 Leave `Goodix_Cache.bin` in its canonical location

Do **not** rename or edit `Goodix_Cache.bin`.

The public Windows exporter in Part 5 reads it directly from:

```text
C:\ProgramData\Goodix\Goodix_Cache.bin
```

`Goodix_Cache.bin` is not one of the final five Linux files. It is the
DPAPI-protected input used to recover the reader's existing 32-byte secret.

Never commit, upload, or share it.

### 3.4 Obtain `gfusb.dll`

Use the `gfusb.dll` from the **same OEM Goodix driver package** that was used
for the Windows environment above. Do not download an arbitrary copy from a
DLL website and do not substitute a DLL from a different driver version.

Copy that file unchanged to:

```text
C:\GoodixMaterialWork\gfusb.dll
```

For the currently qualified driver package the expected file is:

```text
version: 1.1.125.14
size:    5,771,496 bytes
SHA-256: 904eab1d9dbfab2609da361aa6ddba549a9d503f85b4e439b0294908f4cbc7e2
```

If your file does not match these values, stop. The current qualified tooling
is not expecting that DLL.

## Part 4 — Capture the OEM initialization traffic and extract CONFIG90

`target-config-90.bin` is not a Windows file. It is the 224-byte body of the
outbound Goodix A0 logical control command `0x90` observed while the OEM stack
initializes this reader.

The project used Wireshark/TShark with USBPcap on Windows.

### 4.1 Install the capture tools

Install Wireshark with USBPcap support in the Windows environment.

Open PowerShell and list capture interfaces:

```powershell
tshark -D
```

Identify the USBPcap interface associated with the USB controller used by the
VM or physical reader. If you cannot determine which interface is correct,
do not guess: capture all plausible USBPcap interfaces and select the target
traffic afterwards.

### 4.2 Start capture before attaching/initializing the reader

The capture must already be running before the OEM initialization traffic is
produced.

The validated project workflow used a bounded capture and then attached the
reader once by USB passthrough.

After the device appears in Windows and the OEM stack has initialized it,
stop the capture and keep the `.pcapng` file private.

Do not commit or publish the capture. USB captures can contain device-specific
or otherwise private protocol material.

Move the completed `.pcapng` to a private local Linux working directory, for
example:

```text
/home/you/goodix-material-work/oem-init.pcapng
```

### 4.3 Run the CONFIG90 extractor self-test

From the root of the cloned repository:

```bash
python3 tools/device-materials/Extract-Goodix5125Config90.py --self-test
```

Expected result:

```text
GOODIX_CONFIG90_SELFTEST=PASS
```

The self-test is synthetic and offline. It checks fragmented USBPcap frames,
repeated identical CONFIG90 frames, rejection of multiple distinct CONFIG90
bodies, invalid CONFIG90 finalizers, and atomic mode-`0600` output.

### 4.4 Produce `target-config-90.bin`

Run:

```bash
python3 tools/device-materials/Extract-Goodix5125Config90.py \
  --pcap "$HOME/goodix-material-work/oem-init.pcapng" \
  --output "$HOME/goodix-material/target-config-90.bin"
```

The extractor:

1. reads only the supplied local pcapng file;
2. decodes USBPcap records offline using the Python standard library;
3. reconstructs host-to-device bulk traffic on the Goodix OUT endpoint;
4. validates Goodix A0 framing and checksum;
5. selects logical control `0x90`;
6. requires a 224-byte body;
7. validates the CONFIG90 internal finalizer;
8. accepts repeated candidates only if they are byte-identical;
9. fails closed if more than one distinct valid CONFIG90 body is present;
10. writes the output atomically with mode `0600` and never overwrites an
    existing output file.

Successful completion prints:

```text
GOODIX_CONFIG90_EXTRACTION=PASS
output=/home/you/goodix-material/target-config-90.bin
size=224
sha256=<captured CONFIG90 SHA-256>
```

The digest printed here is specific to the user's reader and is consumed by the
manifest generator. No development-reader CONFIG90 digest is an acceptance
criterion.

## Part 5 — Generate `transport-material.bin`

This part is covered by public source tools.

There are two stages:

```text
Windows Goodix_Cache.bin
        ↓
Export-Goodix5125TransportMaterial.ps1
        ↓
transport-material.xfr       (temporary G5125XFR staging record)
        ↓
Finalize-Goodix5125TransportMaterial.py + gfusb.dll
        ↓
transport-material.bin       (final G5125POC runtime record)
```

Both 88-byte files contain sensitive device-specific material. Never commit or
upload either one.

### 5.1 Make the Windows exporter available

The public tools are in the cloned repository at:

```text
tools/device-materials/
```

The two Windows files must remain together:

```text
Export-Goodix5125TransportMaterial.ps1
_Export-Goodix5125TransportMaterial.Core.ps1
```

You can either clone the public repository inside Windows or copy the complete
`tools\device-materials` directory into the Windows VM. The **generated
output must still go to `C:\GoodixMaterialWork`**, not into the repository.

Open **PowerShell as Administrator** and enter the tools directory.

For example, if the repository is at `C:\goodix-27c6-5125`:

```powershell
cd C:\goodix-27c6-5125\tools\device-materials
```

### 5.2 Run the Windows preflight

```powershell
.\Export-Goodix5125TransportMaterial.ps1 -Preflight
```

The preflight checks the canonical cache and Windows environment without
reading the secret or calling DPAPI.

If it reports that the cache is missing or unsuitable, stop and return to
Parts 2 and 3.

### 5.3 Run the secret-free Windows self-test

```powershell
.\Export-Goodix5125TransportMaterial.ps1 -SelfTest
```

This exercises Windows DPAPI with random synthetic bytes. It does **not** read
the Goodix reader secret and it keeps no output file.

The test must complete with `success : True`.

### 5.4 Export the temporary Windows transfer record

Run:

```powershell
.\Export-Goodix5125TransportMaterial.ps1 `
  -OutputPath C:\GoodixMaterialWork\transport-material.xfr
```

The exporter:

1. opens only `C:\ProgramData\Goodix\Goodix_Cache.bin`;
2. rejects reparse-point or malformed cache input;
3. derives the OEM DPAPI optional entropy;
4. calls `CryptUnprotectData`;
5. accepts only an exactly 32-byte, non-zero plaintext;
6. creates an integrity-checked `G5125XFR` record;
7. writes it atomically with a private Windows ACL;
8. reopens and verifies the written bytes;
9. clears temporary secret buffers;
10. never prints the secret.

Expected result:

```text
success          : True
output_size      : 88
secret_disclosed : False
```

and this file exists:

```text
C:\GoodixMaterialWork\transport-material.xfr
```

`transport-material.xfr` is **not** the final Linux file. Do not simply rename
it to `transport-material.bin`.

### 5.5 Move the staging record and `gfusb.dll` to Linux

Copy these two files to a private local Linux working directory using a trusted
local transfer method:

```text
transport-material.xfr
gfusb.dll
```

For example, create the directories first:

```bash
mkdir -p "$HOME/goodix-material-work" "$HOME/goodix-material"
chmod 700 "$HOME/goodix-material-work" "$HOME/goodix-material"
```

After copying, keep the staging record private:

```bash
chmod 600 "$HOME/goodix-material-work/transport-material.xfr"
```

Do not put the staging record inside the Git repository.

### 5.6 Install the Linux finalizer dependency

The finalizer uses Fedora's Python cryptography package:

```bash
sudo dnf5 install python3-cryptography
```

### 5.7 Run the Linux synthetic self-test

From the root of the cloned repository:

```bash
python3 tools/device-materials/Finalize-Goodix5125TransportMaterial.py --self-test
```

Expected result:

```text
GOODIX_TRANSPORT_FINALIZER_SELFTEST=PASS
```

This test uses synthetic secret and producer bytes only. It does not read your
real staging file or OEM DLL.

### 5.8 Create the final `transport-material.bin`

Use absolute paths. For example:

```bash
python3 tools/device-materials/Finalize-Goodix5125TransportMaterial.py \
  --transfer "$HOME/goodix-material-work/transport-material.xfr" \
  --oem-pe "$HOME/goodix-material-work/gfusb.dll" \
  --output "$HOME/goodix-material/transport-material.bin"
```

The finalizer:

1. validates the `G5125XFR` header, target and SHA-256 integrity digest;
2. verifies the exact qualified `gfusb.dll` size and SHA-256;
3. parses the two required producer seeds from the DLL as inert bytes;
4. never loads or executes the DLL;
5. derives the runtime validator;
6. creates the 88-byte `G5125POC` record;
7. writes the final file atomically with mode `0600`;
8. reopens and byte-verifies the output;
9. clears mutable secret and derived-key buffers.

Successful completion prints:

```text
GOODIX_TRANSPORT_FINALIZER=PASS
size=88
sha256=<your generated file SHA-256>
```

Verify the file:

```bash
stat -c 'size=%s mode=%a' "$HOME/goodix-material/transport-material.bin"
head -c 8 "$HOME/goodix-material/transport-material.bin"
echo
```

Expected result:

```text
size=88 mode=600
G5125POC
```

After successful finalization, the temporary `transport-material.xfr` is no
longer needed for normal runtime use. Keep an encrypted recovery copy only if
you deliberately want one; otherwise remove it.

## Part 6 — Verify the five-file bundle

At this point your private Linux-side directory must eventually contain:

```text
goodix-material/
├── target-material-manifest.json
├── transport-material.bin
├── target-config-90.bin
├── gfusb.dll
└── fdt-cache.bin
```

Nothing else is required by the managed importer.

From Linux, enter the directory containing the files and run:

```bash
ls -l
sha256sum \
  target-material-manifest.json \
  transport-material.bin \
  target-config-90.bin \
  gfusb.dll \
  fdt-cache.bin
```

The manifest is generated from the files in this directory. Run the public
generator described in `tools/device-materials/README.md`; never copy digest
values from project history. The runtime recomputes every listed digest and
fails closed on disagreement. File sizes remain protocol invariants: transport
88 bytes, CONFIG90 224 bytes, and FDT cache 13,520 bytes.

## Part 7 — Import the material on Linux

Return to the root of the cloned project repository.

Assuming your complete private bundle is stored at:

```text
/home/you/goodix-material
```

run:

```bash
deployment/managed-install/manage.sh import-materials \
  /home/you/goodix-material
```

Use an **absolute path** to the directory containing the five files.

Successful completion prints:

```text
GOODIX_MANAGED_MATERIAL_IMPORT=PASS
```

The managed importer applies the required root ownership and mode `0600`. The
runtime then performs its own size, digest, format, manifest and device-binding
checks before a secure session can start.

If the importer reports a mismatch, stop and correct the source bundle. Do not
modify the importer or disable validation to force the material through.

## Part 8 — What to keep and what to delete

After a successful import:

- keep an encrypted backup of the five-file bundle if you need disaster
  recovery for the **same physical reader**;
- keep the backup outside Git and outside normal cloud-sync folders;
- remove temporary USB captures when you no longer need them;
- never commit or upload `Goodix_Cache.bin`;
- remove the temporary `G5125XFR` staging record after successful
  finalization unless you intentionally keep an encrypted recovery copy;
- never share the bundle with another user or another reader.

The five-file bundle is not firmware and importing it does not write factory
material back to the sensor.

## Troubleshooting

### `C:\ProgramData\Goodix` does not exist

The OEM Windows stack has not initialized the reader, the OEM driver is not
installed, or the reader is not attached to that Windows instance.

Check Device Manager / `Get-PnpDevice` first. Do not create the directory or
placeholder files manually.

### `goodix.dat` is missing

Allow the normal OEM stack to initialize the same reader. Do not substitute a
`goodix.dat` file from another computer or another fingerprint sensor.

### The Windows exporter says the cache is missing

Confirm that this exact path exists inside the same Windows installation or VM
where the OEM driver initialized the reader:

```text
C:\ProgramData\Goodix\Goodix_Cache.bin
```

Do not point the exporter at a cache from another reader.

### PowerShell refuses to run the script

Use a normal local PowerShell session started **as Administrator**. If your
local execution policy blocks repository scripts, review your Windows policy
rather than copying the script contents into an interactive console. Do not
paste secret output anywhere; the tool itself never prints the secret.

### I have `transport-material.xfr` but no `transport-material.bin`

That is expected after the Windows step. Run the Linux finalizer in Part 5.8
with the matching qualified `gfusb.dll`. Renaming `.xfr` to `.bin` does not
convert the format.

### The Linux finalizer rejects `gfusb.dll`

The current finalizer accepts only the qualified OEM DLL:

```text
size:    5,771,496 bytes
SHA-256: 904eab1d9dbfab2609da361aa6ddba549a9d503f85b4e439b0294908f4cbc7e2
```

Use the DLL from the exact OEM driver package. Do not patch the finalizer to
skip this validation.

### I have a PCAP but no `target-config-90.bin`

Run the public offline extractor from the repository root:

```bash
python3 tools/device-materials/Extract-Goodix5125Config90.py \
  --pcap /absolute/path/to/capture.pcapng \
  --output /absolute/path/to/target-config-90.bin
```

If it reports that no valid CONFIG90 was found, confirm that the capture was
started before OEM initialization and contains the reader's host-to-device USB
traffic. Do not manually cut 224 bytes from Wireshark.

If it reports multiple distinct valid CONFIG90 bodies, treat the capture as
ambiguous and repeat a clean bounded initialization capture instead of choosing
one manually.

### The CONFIG90 extractor succeeds but the runtime later rejects the material

Extraction and runtime qualification are separate checks. The extractor proves
that the capture contains a structurally valid CONFIG90 body. The current
runtime remains qualified against its complete reference material set and may
reject a different reader-specific CONFIG90 hash. Do not disable the runtime
validation; this is a portability/qualification issue rather than an extraction
failure.

### Can I use another reader's five files?

No. The secret and cache material are tied to the same physical reader.

### Can I generate a random 32-byte PSK instead?

No. The project is factory-preserving and does not provision replacement PSKs.

### Can I flash firmware or run ClearApp to make the reader accept new material?

No. Flash/IAP/ClearApp, OTP writes and persistent reprovisioning are outside
the supported design.

## Technical reference: the two 88-byte transport records

This section is for developers. A normal installer does not need to construct
these records manually.

`G5125XFR` is the temporary Windows-to-Linux transfer envelope. Its 24-byte
little-endian header contains the magic, version, flags, VID, PID, bounded
secret length, reserved field and payload length. It is followed by the
32-byte DPAPI plaintext and a SHA-256 digest of the header plus plaintext. The
digest detects transfer damage; it does not encrypt the secret.

`G5125POC` is the runtime format stored as `transport-material.bin`. Its
24-byte header identifies version 1, the target VID/PID, material kind, secret
length and validator length. The payload contains the 32-byte device secret
and the 32-byte validator derived from producer data in the pinned OEM DLL.

The conversion exists so that the runtime can validate binding before it uses
the secret for TLS.

This is an acquisition path, not PSK provisioning: the project recovers the
reader's existing factory material and never invents, replaces or writes a new
factory PSK.
